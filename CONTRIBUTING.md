# Работа с Git

`main` содержит проверенную версию приложения. Постоянная ветка `develop` не нужна.

1. Создать короткоживущую ветку от актуального `main`: `feature/<задача>` для новой функциональности, `fix/<задача>` для исправлений или `docs/<задача>` для документации.
2. Делать небольшие смысловые коммиты. Сообщения: `fix: ...`, `feat: ...`, `test: ...`, `docs: ...`, `ci: ...`.
3. Перед публикацией выполнить `./gradlew assembleDebug testDebugUnitTest` и `git diff --check`.
4. Отправить ветку на GitHub и открыть PR с описанием поведения, проверок и ограничений.
5. После проверки слить PR через squash-merge: один законченный PR — один коммит в `main`.
6. Обновить локальный `main` через `git pull --ff-only` и удалить слитую рабочую ветку.

Документация, сообщения коммитов и заголовки/описания PR должны описывать только проект, изменения, проверки и ограничения. Не добавлять самоописание автора, названия инструментов генерации, ссылки на чат или рекламную атрибуцию. Названия веток отражают задачу, а не способ выполнения работы.

Независимые задачи начинаются от `main`. Если задача зависит от ещё не слитого PR, можно временно создать ветку от его вершины и открыть второй PR в первую ветку. После слияния первого PR второй переносится на `main` с сохранением только своих коммитов.

Не переписывать историю `main`, не отправлять туда force-push. Если опубликованный коммит содержит ошибку, исправить её новым коммитом или revert.

Версии отмечаются тегами `v0.x.y` после проверки на реальных устройствах. APK и локальные настройки SDK/Gradle в Git не добавляются.

Для этого проекта ближайшие задачи разделены так:

- Стабилизация Stage 1–3: рабочая версия приложения, исправления подключения, спецификация.
- Stage 4: обработка отмены, ошибок хранения и передачи, статусы, регрессионные тесты.
- Будущий дизайн по макету Figma — отдельный PR после этапа 4.
